# v.2.3.0
Versión menor: Verify cambia de comportamiento y se añade NeedsRehash, sin romper la API pública.
CAMBIO DE COMPORTAMIENTO: Verify lee el algoritmo (HMACSHA1, HMACSHA256 o HMACSHA512), las iteraciones y la longitud de la sal de la cabecera del propio hash, y no de la configuración. Un hash guardado se sigue verificando aunque se cambien KeyDerivationAlgorithm, IterCount o SaltLength. Hasta la 2.2.0, cambiar cualquiera de los tres hacía que todos los hashes guardados dieran false. La marca de formato (FormatMarker) y la longitud de la cabecera (HeaderByteLength) sí tienen que seguir siendo las mismas.
- Restricción nueva: un hash con más de 10.000.000 iteraciones o con una sal de más de 1024 bytes da false sin calcular nada (hasta la 2.2.0 se verificaba si la configuración coincidía). No configurar IterCount por encima de 10.000.000: Create seguiría creando hashes que Verify rechaza.
- Un hash con 0 iteraciones, con la sal vacía, con un algoritmo desconocido, o cortado o alargado, sigue dando false sin calcular nada.
Nuevo: NeedsRehash(hash) dice si un hash se creó con un algoritmo, unas iteraciones o una longitud de sal distintos de los de la configuración actual (también da true si el hash es nulo o está mal formado). Para subir las iteraciones sin invalidar nada: cambiar la configuración y, después de cada Verify correcto, si NeedsRehash da true, guardar el hash nuevo de Create con la contraseña que acaba de entrar. En IPasswordService es un miembro con implementación por defecto que devuelve false, así que una implementación propia sigue compilando.
- NeedsRehash compara con "distinto", no con "menor": bajar las iteraciones también pide regenerar. Si durante un despliegue dos instancias tienen configuraciones distintas, cada una regenerará los hashes de la otra en cada inicio de sesión hasta que coincidan.
- Create lanza si el servicio está desactivado (Enabled = false); Verify y NeedsRehash no lo comprueban. Con el servicio desactivado, no llamar a Create para regenerar.
- Verify sigue aplicando la política actual de contraseñas (longitud mínima, etc.) antes de comprobar el hash: si se endurece, las contraseñas antiguas que no la cumplan dejan de verificar.
Obsoleto (KPY0004): EncryptionSettings.AlgorithmName y EncryptionSettings.DefaultAlgorithmName. No hacen nada: el algoritmo lo marca KeyDerivationAlgorithm al crear el hash, y al verificar se lee del hash. Hasta la 2.2.0, Verify exigía que AlgorithmName coincidiera con el algoritmo del hash, y con KeyDerivationAlgorithm 0 o 2 y AlgorithmName por defecto ninguna contraseña verificaba. Se eliminan en la 3.0.0.
- El paquete se compara al empaquetar con la API pública de la 2.2.0 (validación de paquete).

# v.2.2.0
Versión menor y no parche: corrige un fallo de Verify y cambia su comportamiento con un hash nulo o vacío, sin cambiar la API pública.
CAMBIO DE COMPORTAMIENTO: Verify(contraseña, hash) con el hash nulo, vacío o sólo con espacios devuelve false. Hasta la 2.1.1 lanzaba SharedException (la documentación decía ArgumentException). Quien capturase esa excepción para tratar "usuario sin contraseña" tiene que mirar el false. Con la contraseña nula o vacía ya devolvía false y sigue igual.
Corrección de un fallo: Verify aceptaba un hash con un código de algoritmo desconocido en la cabecera (cualquier valor distinto de 0, 1 y 2) y lo trataba como HMACSHA256. Con la configuración por defecto, un hash bueno con esa parte de la cabecera cambiada se daba por válido. Ahora es un hash mal formado y devuelve false. Los hashes creados por Create no cambian y se siguen verificando igual.
- Tests nuevos: contraseña incorrecta, cualquier byte del hash cambiado, hash nulo o vacío, hash mal formado, cortado o con bytes de más, de otro algoritmo o con otro número de iteraciones o de longitud de sal.
- El paquete se compara al empaquetar con la API pública de la 2.1.1 (validación de paquete).

# v.2.1.1
Parche: corrige un fallo de la generación de contraseñas, sin cambiar la API pública.
Corrección de un fallo: CreateRandom duplicaba la contraseña cuando los caracteres obligatorios (dígito, especial, minúscula, mayúscula y el de caracteres únicos) ya llegaban a RequiredMinLength. Salía del doble de largo y con cada carácter repetido (por ejemplo "1@aB1@aB"), y con RequiredUniqueChars devolvía siempre null. Ahora sólo se rellena cuando falta longitud, así que la contraseña tiene exactamente los caracteres obligatorios.
- Afecta sólo a quien configura una longitud mínima menor o igual que el número de requisitos activos. Con la configuración por defecto (longitud mínima 6 y como mucho 5 requisitos) o con una longitud mínima mayor, el resultado no cambia.
- Con esa configuración y sin RequiredUniqueChars, las contraseñas generadas tienen ahora la mitad de largo; con RequiredUniqueChars, CreateRandom devuelve una contraseña donde antes devolvía null.

# v.2.1.0
Versión menor y no parche: corrige vulnerabilidades y un fallo sin cambiar la API pública, pero hereda el cambio de comportamiento de Kitpymes.Core.Logger 2.1.0 (abajo).
Corrección de seguridad: Kitpymes.Core.Api 2.0.0, a través de Kitpymes.Core.Logger 2.0.0, traía dependencias con vulnerabilidades conocidas, que heredaba quien instalaba Security.
- Alta: Microsoft.Data.SqlClient 5.0.1 (GHSA-98g6-xh36-x2p7) y Azure.Identity 1.6.0 (GHSA-5mfx-4wcx-rv27). Moderada: Azure.Identity (GHSA-wvxc-855f-jvrv, GHSA-m5vv-6r4h-3vj9), MailKit 2.6.0 (GHSA-9j88-vvj5-vhgr) y MimeKit 2.6.0 (GHSA-g7hc-96xr-gvvx).
- Pasa a Kitpymes.Core.Api 2.1.0 (que usa Kitpymes.Core.Logger 2.1.0), que las corrige.
- Sin cambios en la API pública. El log por email de Logger cambia de comportamiento en la 2.1.0 (ver sus release notes): quien instala Security recibe Serilog 4.x y MailKit 4.x como dependencias transitivas (NU1605 si fijaba Serilog 3.x o MailKit 2.x) y los lotes que fallan se reintentan más tarde.
Corrección de un fallo: CreateRandom con RequiredUniqueChars devolvía null al azar (más o menos una de cada ocho veces con la configuración de los tests), porque el relleno hasta la longitud mínima podía repetir un carácter. Ahora sólo elige caracteres que no están ya en la contraseña.

# v.2.0.0
Versión mayor: rompe a quien venga de la 1.0.5 (la última publicada en NuGet, .NET 7). Abajo, qué cambia y cómo migrar.

- Requiere .NET 10 o superior.
- Usa las librerías Kitpymes ya migradas desde NuGet (Shared 2.0.1, Api 2.0.0); quien la use debe migrar también esas (ver sus release notes).
- El código pasa a github.com/kitpymes/kitpymes-core-security y el paquete se publica desde GitHub Actions.

## Cambios incompatibles y cómo migrar desde 1.0.5

1. Espacios de nombres: antes todo estaba en Kitpymes.Core.Security. Ahora hay espacios por función: Authentication (Cookies, JsonWebToken, OAuth, cada uno con Extensions y Settings), Authorization (Requirements y Settings), Encryptor y Password (cada uno con Extensions y Settings).

2. Autorización (nuevo): AuthorizationSettings, PoliciesSettings y DefaultPolicySettings, requisitos por permiso y por rol (PermissionRequirement, RoleRequirement) y AuthorizationCollectionExtensions / AuthorizationApplicationBuilderExtensions para registrarla.

3. Eliminado: UnauthorizedAccessMiddleware.

4. Cifrado (Encryptor) fuera de Windows
   - Antes, ProtectKeysWithDpapi se aplicaba siempre y en Linux lanzaba PlatformNotSupportedException. Ahora sólo se aplica en Windows; en Linux las claves se guardan sin cifrar en la carpeta de PersistKeysToFileSystem, que hay que proteger.
   - La carpeta por defecto pasa de "bin\keys" a "bin/keys" (en Linux se creaba una carpeta llamada literalmente "bin\keys").
